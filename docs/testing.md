# Тестирование

В проекте **221 автоматический тест** на пяти уровнях, плюс статические проверки стиля и типов. Всё это запускается в CI на каждый push. Идея простая: чем ниже уровень, тем больше тестов и тем быстрее они работают; чем выше — тем ближе к тому, что увидит живой человек.

| Уровень | Файлы | Тестов | Что нужно | Время |
|---|---|---|---|---|
| Unit: домен | `tests/unit/test_domain.py` | 61 | ничего | < 1 с |
| Unit: имитатор кошелька | `tests/unit/test_mockwallet.py` | 15 | ничего | < 1 с |
| Unit: сервисы | `tests/unit/test_services.py` | 31 | ничего | ~1 с |
| Архитектура | `tests/test_architecture.py` | 43 | ничего | < 1 с |
| Контракт: память | `tests/contract/test_memory.py` | 16 | ничего | < 1 с |
| Контракт: PostgreSQL | `tests/contract/test_postgres.py` | 16 | PostgreSQL | ~2 с |
| Интеграция: HTTP API | `tests/integration/test_api.py`, `test_checkout_flow.py` | 29 | ничего | ~3 с |
| Сквозные в браузере | `tests/e2e/test_e2e.py` | 10 | Chromium (+ PostgreSQL по желанию) | ~1,5 мин |

Без базы и браузера проходят 195 тестов, 16 контрактных тестов PostgreSQL пропускаются с понятной причиной, сквозные включаются отдельно.

## Как запустить

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pip install -e . --no-deps

pytest                                   # всё, кроме браузера (PostgreSQL — если задан TEST_DATABASE_URL)
pytest tests/unit -q                     # только быстрые unit-тесты
ruff check . && ruff format --check .    # стиль
mypy                                     # типы в режиме --strict
```

Контрактные тесты на PostgreSQL:

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16-alpine
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres pytest tests/contract
```

Сквозные тесты в браузере:

```bash
playwright install chromium                                  # один раз
RUN_E2E=1 pytest tests/e2e                                   # сервер на хранилище в памяти
RUN_E2E=1 E2E_DATABASE_URL=postgresql://… pytest tests/e2e   # сервер на PostgreSQL, как в production
```

## Что проверяет каждый уровень

### Unit-тесты домена

Чистые функции и сущности без ввода-вывода. Примеры:

- **Деньги:** `parse_amount` принимает `"25000000"` и числа больше точности `float` без потерь, но отвергает `"12.5"`, `"-5"`, `"1e6"`, `"١٢"` (арабские цифры — `\d` в Python совпадает и с ними), `True` (в Python `bool` — подкласс `int`) и числа длиннее 30 цифр; `parse_units` и `format_units` переводят `"12.5"` ↔ `12500000` туда и обратно.
- **Конечный автомат:** каждый разрешённый переход работает, каждый запрещённый бросает `InvalidStateError` с кодом `payment_intent_unexpected_state`. Отдельно проверено, что `requires_payment_method → succeeded` нельзя даже при «достаточных» подтверждениях.
- **Повторная попытка:** после неудачи платёж возвращается в `requires_payment_method`, у него заполняется `last_payment_error`, и новая попытка его очищает.
- **Возвраты:** нельзя вернуть больше, чем получено; несколько частичных возвратов складываются; снятие резерва при неудаче.
- **Комиссия:** округляется вверх: 1 % от 25 USDT — 0.25 USDT, а 1 % от 1 минимальной единицы — 1, а не 0, иначе мелкие платежи шли бы без комиссии.
- **Сессия:** срок жизни от 5 минут до 24 часов; `{CHECKOUT_SESSION_ID}` подставляется в `success_url`.

### Unit-тесты MockWallet

Имитатор тоже код, и он тоже может ошибаться. Проверяется, что высота цепочки — функция от времени, подтверждения считаются как в Ethereum, у каждого тестового кошелька свой исход, деньги списываются сразу, а зачисляются при попадании в блок, провалившаяся транзакция возвращает деньги отправителю, запрос истекает через 15 минут, а `send_from_treasury` идемпотентен по `reference`.

### Unit-тесты сервисов

Сервисы собираются через тот же `container.py`, но с подменами из `tests/support/fakes.py`: `FakeClock`, `SequentialIds`, `PlainPasswordHasher`, `RecordingWebhookSender` и `StubWallet`. Время двигается вручную, поэтому тест «дождаться 3 подтверждений» занимает микросекунды. Отдельные тесты проверяют неприятные ситуации:

- кошелёк вернул транзакцию **на другую сумму** — платёж не засчитан (`amount_mismatch`);
- повторная сверка уже оплаченного платежа не создаёт вторую проводку и не шлёт событие второй раз;
- медленная сеть (кошелёк Дэйва) и транзакция, упавшая в сети (кошелёк Евы), заканчиваются правильными статусами;
- продавец отменяет платёж ровно в тот момент, когда покупатель подтвердил его в кошельке, — отмена не проходит, платёж переходит в `processing`;
- вебхук: сервер магазина отвечает 500 — повторы через 1, 5, 15, 60, 360 минут и статус `failed` после шестой попытки;
- возврат больше баланса продавца — ошибка `balance_insufficient`;
- провалившийся возврат — компенсирующая проводка, баланс восстановлен.

### Архитектурные тесты

«Фитнес-функции» — тесты не поведения, а структуры кода. Разбирают импорты каждого файла через `ast` и проверяют правило зависимостей (подробно — в [solid.md](solid.md#d--dependency-inversion-principle)). 43 теста — это параметризация по файлам: каждый файл `domain` и `application` проверяется отдельно, поэтому сообщение об ошибке сразу называет виновника.

### Контрактные тесты репозиториев

Класс `RepositoryContract` описывает поведение, которого сервисы ждут от хранилища, а два наследника прогоняют его на памяти и на PostgreSQL. Среди проверок: курсорная пагинация, оптимистическая блокировка, суммы размером 2²⁰⁰ и кириллица в `metadata` без искажений, одна транзакция кошелька не может оплатить два платежа, одна проводка `payment` на платёж, outbox отдаёт только созревшие доставки, `try_begin` для ключа идемпотентности атомарен, а исключение внутри `transaction()` откатывает **все** изменения. Это и есть автоматическая проверка принципа подстановки Лисков.

### Интеграционные тесты HTTP

Настоящее приложение FastAPI через `httpx.ASGITransport`, без сети. Проверяют то, что видит интегратор: коды ответов, формат ошибок `{"error": {…}}`, Basic- и Bearer-авторизацию, 404 на чужой объект, идемпотентность с заголовком `Idempotent-Replayed`, пагинацию, лимит тела 32 КБ, заголовки безопасности, ограничение частоты (и что его нельзя обойти подделкой `X-Forwarded-For`), защиту вебхуков от SSRF и полный сценарий «сессия → оплата → вебхук с правильной подписью → возврат → баланс».

### Сквозные тесты в браузере

Playwright запускает настоящий процесс `python -m cryptopay`, пример магазина `examples/shop.py` и Chromium. Блок MockChain — раз в секунду, чтобы тест не ждал долго.

| Тест | Сценарий |
|---|---|
| `test_customer_pays_with_alice_and_sees_the_stamp` | Главная → «Попробовать оплату» → кошелёк → Алиса → прогресс подтверждений → печать «Оплачено» |
| `test_insufficient_funds_then_retry_with_another_wallet` | Боб: «Недостаточно средств» → «Попробовать снова» → Алиса → оплачено |
| `test_customer_rejects_in_wallet` | Покупатель нажал «Отклонить» |
| `test_wallet_declines` | Кэрол: кошелёк отклоняет платёж |
| `test_transaction_fails_in_the_network` | Ева: транзакция падает в сети |
| `test_shop_integration_with_webhook` | Магазин создаёт сессию по API-ключу → оплата → возврат на `/thanks` → вебхук отмечает заказ оплаченным |
| `test_dashboard_refund` | Кабинет: платёж → частичный возврат 5 USDT → «Возврат дошёл до покупателя» → баланс |
| `test_dashboard_payment_link_and_developers` | Регистрация → платёжная ссылка в BTC → выпуск ключа → адрес вебхука → тело события |
| `test_mockchain_explorer_shows_the_payment` | Оплата Алисой и её транзакция в обозревателе MockChain |
| `test_swagger_ui_works_under_strict_csp` | Swagger UI работает при строгом CSP |

Каждая страница подключается к `ConsoleWatch`: **любая ошибка в консоли браузера** — исключение в JavaScript или нарушение CSP — валит тест, даже если на экране всё выглядит нормально. Скриншоты из этих прогонов лежат в `docs/screenshots` и используются в отчёте — то есть картинки в отчёте не нарисованы, а сняты с работающей системы.

## Статические проверки

- **ruff** — стиль и линтер с наборами правил pycodestyle, pyflakes, isort, bugbear, правил безопасности из `bandit` (`S`), асинхронного кода (`ASYNC`), упрощений (`SIM`) и модернизации синтаксиса (`UP`);
- **ruff format** — единое форматирование;
- **mypy --strict** — полная проверка типов во всех 69 файлах пакета: ни одного `Any` без явного намерения, ни одной функции без аннотаций.

## Непрерывная интеграция

`.github/workflows/ci.yml` на каждый push и pull request:

1. ставит зависимости и поднимает PostgreSQL 16 как сервис;
2. `ruff check` и `ruff format --check`;
3. `mypy`;
4. `pytest` — unit, архитектурные, контрактные (память **и** PostgreSQL) и интеграционные;
5. ставит Chromium и запускает сквозные тесты с сервером поверх PostgreSQL;
6. собирает Docker-образ.

Render разворачивает новую версию автоматически после коммита в `main`, так что красный CI — сигнал не мёржить.

# Безопасность

Платёжная система — это код, который решает, кому достанутся деньги. Даже в учебном проекте мы старались закрыть типичные дыры из OWASP Top 10 и те, что характерны именно для платежей: двойное списание, подделка уведомлений, доверие к данным внешней системы. Ниже — угрозы и то, как каждая закрыта, со ссылками на код.

| Угроза | Защита | Где |
|---|---|---|
| Двойное зачисление одного платежа | Оптимистическая блокировка + `UNIQUE wallet_tx_id` + одна проводка `payment` на платёж | `payment_service.py`, `001_initial_schema.sql` |
| Повтор запроса создаёт второй платёж | `Idempotency-Key`, атомарное «занятие» ключа | `idempotency_service.py` |
| Двойная отправка возврата | Отправка из кошелька идемпотентна по `reference = re_…` | `refund_service.py`, `mockwallet/service.py` |
| Кошелёк сообщил не ту сумму | Сверка суммы и валюты транзакции с платежом → `amount_mismatch` | `PaymentService._apply` |
| Поддельный вебхук магазину | Подпись HMAC-SHA256 с секретом `whsec_…`, проверка за постоянное время | `webhooks.py`, `examples/shop.py` |
| Перехват и повтор вебхука (replay) | Время `t` внутри подписи, магазин отбрасывает подписи старше 5 минут | `examples/shop.py` |
| SSRF через адрес вебхука | Только `https`, запрет `localhost`, частных сетей, `169.254.169.254`, логина в URL; без следования редиректам | `DefaultWebhookUrlPolicy`, `HttpxWebhookSender` |
| Утечка секретного ключа из базы | Хранится только SHA-256 ключа и последние 4 символа | `account_service.py` |
| Утечка паролей из базы | scrypt (N = 2¹⁴, r = 8, p = 1), своя соль на каждый пароль | `ScryptPasswordHasher` |
| Перебор паролей | 20 запросов в минуту на вход и регистрацию с одного IP | `app.py`, `middleware.py` |
| Перебор e-mail по времени ответа | Для несуществующего e-mail всё равно проверяется «пустой» хэш | `AccountService.sign_in` |
| Подмена алгоритма JWT (`alg=none`) | Явный список `algorithms=["HS256"]` | `infrastructure/auth.py` |
| Доступ к чужим платежам (IDOR) | Каждый запрос фильтруется по `merchant_id`; чужой объект → 404, а не 403 | все сервисы |
| XSS | Строгий CSP без `unsafe-inline`; данные вставляются только через `textContent` | `middleware.py`, `public/assets/js/ui.js` |
| Clickjacking | `X-Frame-Options: DENY`, `frame-ancestors 'none'` | `middleware.py` |
| Тяжёлые запросы (DoS) | Тело не больше 32 КБ, лимиты частоты, ограничение длины всех полей | `BodySizeLimitMiddleware`, `schemas.py` |
| Подделка IP для обхода лимитов | Учитывается только адрес, добавленный доверенным прокси (`TRUST_PROXY`) | `RateLimiter` |
| SQL-инъекции | Только параметризованные запросы psycopg | `postgres/repositories.py` |
| Невалидные суммы | Только цифры `[0-9]`, без `float`, без `bool`, не длиннее 30 знаков | `domain/money.py` |

## Деньги и состояния

**Двойное зачисление** — главный страх любой платёжной системы. Мы защищаемся от него на трёх уровнях сразу:

1. **Код.** `PaymentService.sync()` сравнивает `version` платежа до и после обращения к кошельку. Если кто-то успел изменить платёж (например, страница оплаты и фоновая задача сработали одновременно), результат текущего прохода выбрасывается.
2. **Конечный автомат.** Перейти в `succeeded` можно только из `processing`. Второй вызов `mark_succeeded` на уже оплаченном платеже бросит `InvalidStateError`.
3. **База данных.** Даже если и код, и автомат ошибутся, PostgreSQL не даст записать два платежа с одной транзакцией кошелька (`UNIQUE wallet_tx_id`) и две проводки `payment` на один платёж (частичный уникальный индекс).

**Не доверять внешней системе.** Кошелёк — чужой код. Поэтому мы не верим статусу «оплачено» на слово: сверяем сумму и валюту транзакции, считаем подтверждения сами и засчитываем платёж только при `confirmed` и достаточном числе блоков.

**Не доверять возврату покупателя.** Страницу `success_url` магазина можно открыть руками, не заплатив. В документации и в примере `examples/shop.py` заказ отмечается оплаченным **только по подписанному вебхуку**.

## Аутентификация

- **Продавцы** входят по e-mail и паролю (8–128 символов). Пароли хэшируются scrypt — функцией, которая специально медленная и требует много памяти, поэтому перебор украденных хэшей стоит дорого. Параметры хранятся прямо в строке хэша `scrypt$n$r$p$соль$хэш`, так что их можно усилить позже, не ломая старые пароли.
- **Сессия кабинета** — JWT, подписанный HS256 секретом `JWT_SECRET` (не короче 32 символов, в production обязателен). Время жизни — `SESSION_TTL`, по умолчанию 12 часов. Токен хранится в `localStorage` браузера и уходит в заголовке `Authorization`, а не в cookie, — поэтому CSRF-атака невозможна в принципе: чужой сайт не может заставить браузер подставить этот заголовок. Обратная сторона — токен доступен JavaScript страницы, поэтому так важен строгий CSP (ниже).
- **Сервер магазина** использует секретный ключ `sk_test_…` (48 случайных hex-символов). В базе — только SHA-256 и последние 4 символа для отображения `sk_test_…a1b2`. Ключ показывается один раз; выпуск нового сразу отзывает старый.
- **Разделение прав.** Ключом API нельзя управлять аккаунтом (сменить название, выпустить новый ключ) — только сессией кабинета. Если ключ утечёт с сервера магазина, злоумышленник не сможет перевыпустить его и запереть владельца снаружи.

## Вебхуки

Подпись устроена как у Stripe:

```
cryptopay-signature: t=1794219546,v1=hex(HMAC-SHA256(whsec_…, "1794219546.<сырое тело>"))
```

- Время входит в подписанную строку, поэтому перехваченный запрос нельзя «проиграть» позже: магазин отбрасывает подписи старше 5 минут.
- Сравнение — `hmac.compare_digest`, за постоянное время: по времени ответа подпись не подобрать.
- Секрет свой у каждого адреса, показывается один раз.

**SSRF.** Продавец сам вводит адрес, на который наш сервер будет слать POST-запросы. Без защиты он мог бы указать `http://169.254.169.254/` (метаданные облака с ключами доступа) или `http://localhost:5432`. `DefaultWebhookUrlPolicy` в production разрешает только `https://` на внешние адреса и запрещает `localhost`, `*.local`, `*.internal`, частные и служебные сети (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, 100.64/10, IPv6 `::1`, `fc00::/7`, `fe80::/10` и IPv4, записанный как IPv6 — `::ffff:127.0.0.1`) и логин/пароль в URL. HTTP-клиент не следует редиректам — иначе внешний адрес мог бы перенаправить запрос внутрь. В режиме разработки `http://localhost` разрешён, чтобы можно было запустить `examples/shop.py`.

## Заголовки и браузер

Middleware `SecurityHeadersMiddleware` — аналог `helmet` из мира Node.js — добавляет к каждому ответу:

```
content-security-policy: default-src 'self'; script-src 'self'; script-src-attr 'none'; style-src 'self';
                         img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none';
                         frame-ancestors 'none'; base-uri 'self'; form-action 'self'
x-content-type-options: nosniff
x-frame-options: DENY
referrer-policy: no-referrer
cross-origin-opener-policy: same-origin
permissions-policy: camera=(), microphone=(), geolocation=(), payment=()
strict-transport-security: max-age=31536000; includeSubDomains     (только в production)
```

`script-src 'self'` без `unsafe-inline` означает, что даже если злоумышленнику удастся вставить `<script>` в описание товара, браузер его не выполнит. Для надёжности интерфейс вообще не использует `innerHTML` с данными: все строки вставляются через `textContent`. Сквозные тесты падают при любой ошибке CSP в консоли.

Для Swagger UI (`/docs`) политика чуть мягче — ему нужны встроенные стили, — и это единственное исключение.

## Ограничение частоты

| Что | Лимит с одного IP |
|---|---|
| Вход и регистрация в кабинете | 20 в минуту |
| Чтение страницы оплаты | 120 в минуту |
| Кнопка «Оплатить» и демо-оплата | 30 в минуту |
| Действия в окне кошелька | 60 в минуту |

При превышении — `429` с заголовком `Retry-After`. IP клиента берётся из `X-Forwarded-For` **только** на столько прокси, сколько указано в `TRUST_PROXY` (на Render — 1). Поэтому клиент не может подставить чужой IP в заголовок и получить новый лимит — это проверено интеграционным тестом.

## Что мы сознательно не делали

Это учебный проект в тестовом режиме, поэтому часть мер production-уровня осталась за рамками. Мы их перечисляем, чтобы было понятно: это не забыли, а отложили.

- **Живой режим и настоящие деньги.** Все ключи — `sk_test_…`, `livemode` всегда `false`.
- **Двухфакторная аутентификация** продавцов и подтверждение e-mail.
- **Ротация ключей с периодом перекрытия.** Сейчас новый ключ отзывает старый сразу.
- **Распределённый rate limit.** Лимиты хранятся в памяти процесса; для нескольких экземпляров нужен Redis.
- **Аудит действий** продавца (кто и когда сделал возврат) отдельно от журнала событий.
- **Шифрование секретов вебхуков в базе.** Сейчас `whsec_…` хранится открыто — подписывать без самого секрета невозможно, а для шифрования нужен внешний KMS.
